# Monthly Music Arena data release

The full pipeline: pull new battles from GCP → preprocess → push to HuggingFace → wait for parquet conversion → regenerate the leaderboard → stage the frontend snapshot → make a local commit and hand off. Run **one step at a time**, showing output and getting confirmation before any public or destructive action (HF push, git commit). **Do not push the main-repo commit and do not open a PR** — the maintainer reviews and does that themselves.

## When to run

Run month M's release **after month M has ended** — the downloader auto-detects the end date as "end of the previous calendar month", so June data must be processed in July (or later). Example: May 2026 release was run on 2026-06-04.

## Prerequisites (all already set up on this machine)

1. **Working dir**: `~/music-arena-leaderboard`.
2. **Activate the venv in every Bash call** — shell state does not persist between tool calls: `source ~/music-arena-leaderboard/.venv/bin/activate`. `ma-comp` lives in the venv, not on PATH.
3. **HF dataset clone**: in-tree at `./music-arena-dataset/` (remote `git@hf.co:datasets/music-arena/music-arena-dataset`). *Not* at `$HOME/music-arena-dataset` as the old shell script assumed.
4. **Secrets**: `GCP_BUCKET_SERVICE_ACCOUNT`, `METADATA_BUCKET`, `AUDIO_BUCKET`, HF token cached in `~/.cache/music_arena/secrets/`. No interactive prompts needed.
5. **git-lfs** is installed; the dataset repo tracks `audio_files/**/*.mp3`.
6. `ma-comp` dispatches each subcommand **inside Docker** (auto-builds the image on first run). On this machine, Docker runs as **root**, so anything it writes under `~/.cache/music_arena` and `components/leaderboard/results` is root-owned.
7. On this machine: **no passwordless `sudo`** and **`gh` is not installed** — plan around both.

Use TaskCreate to track the seven steps and mark each `completed` before starting the next.

## Naming for the new month

- **Battle-data folder tag** (sequentially numbered): find current latest with
  `ls -1 ~/.cache/music_arena/bucket/dataset/battle_data/ | sort | tail -1`.
  Example: latest is `10-2026MAY` → June is `11-2026JUN`, July is `12-2026JUL`.
- **HF README config name**: `YYYY_MM` (e.g. May = `2026_05`, June = `2026_06`). Auto-generated by `update_hf_readme.py`; no manual edit.
- **Frontend snapshot dir**: end-of-month `YYYYMMDD` (May = `20260531`, June = `20260630`).
- **Feature branch**: `26MM-update` (May was `2605-update`, June is `2606-update`), cut from `main`.

## Steps

### Step 1 — Download new battle data from GCP

```
ma-comp leaderboard download
```

- Auto-detects start (latest existing local log) and end (end of previous month). Incremental/idempotent.
- Report the download range and "Logs downloaded / Audio downloaded" counts back to the maintainer.

### Step 2 — Preprocess into HF dataset format

```
ma-comp leaderboard -s preprocess
```

- Use `-s` (skip-build) from step 2 onward — the image is already built.
- Writes to `~/.cache/music_arena/bucket/dataset/{battle_data,audio_files,metadata}/<TAG>`.
- Confirm the new tag appears (`ls -1 ~/.cache/music_arena/bucket/dataset/battle_data/`) and note its stats from `metadata/<TAG>.md`.

### Step 3 — Push to the HuggingFace dataset ⚠️ external + irreversible

**Ask the maintainer before pushing.** This publishes data publicly. Summarize the month's stats first (battles, votes A/B/TIE/BOTH_BAD, instrumental vs vocal, unique users, model appearances) so they can eyeball. Audio exclusion must be driven entirely by `release_audio_publicly: false` in `systems/registry.yaml` — preprocess should read this flag per-model at run time rather than hardcoding a model list, so any model marked non-public (whatever the reason) is automatically excluded from the audio release without a code change. Check `metadata/<TAG>.md`'s excluded-audio count and the list of excluded model names look right before pushing.

```
cd ~/music-arena-leaderboard/music-arena-dataset
TAG=<the new tag from step 2, e.g. 11-2026JUN>
DS=~/.cache/music_arena/bucket/dataset

git pull --no-edit
git lfs install
git lfs track "audio_files/**/*.mp3"

cp -r "$DS/battle_data/$TAG"  ./battle_data/
cp -r "$DS/audio_files/$TAG"  ./audio_files/
cp    "$DS/metadata/$TAG.md"  ./metadata/

# Regenerate README YAML configs from battle_data (host venv; package is installed there)
cd ~/music-arena-leaderboard/components/leaderboard
python -m ma_leaderboard.update_hf_readme ~/music-arena-leaderboard/music-arena-dataset

cd ~/music-arena-leaderboard/music-arena-dataset
git add -A
git diff --staged --stat   # sanity: N battle jsons + M mp3 (as LFS pointers) + README + metadata
git commit -m "Add <Month> YYYY data"
```

**Verify LFS pointers before pushing** — the mp3s should be staged as pointer text, not raw bytes:

```
git show :audio_files/$TAG/<somefile>.mp3 | head -3
# expect: version https://git-lfs.github.com/spec/v1
```

**Lower LFS concurrency** to avoid HF's 1000-req/5min rate limit (learned the hard way on the April run — default concurrency=8 hit the limit repeatedly):

```
git config lfs.concurrenttransfers 2
git config lfs.transfer.maxretries 10
```

Push using a `Monitor` retry loop rather than `sleep`-polling. The loop should retry `git push` on failure, waiting ~330s between attempts, up to ~10 tries, and emit only the meaningful lines (`Uploading LFS objects:`, `main ->`, `error:`, `fatal:`). With concurrency=2 the April run succeeded on attempt 1.

### Step 3.5 — Sanity check (informational)

```
ma-comp leaderboard -s sanity-check
```

Right after a push, the HF datasets-server frequently returns **HTTP 500 / "busier than usual"** while it re-converts parquet — this is expected, not a failure. **The git push itself is authoritative**; confirm it landed via git:

```
cd ~/music-arena-leaderboard/music-arena-dataset
git log -1 origin/main
```

### Step 4 — Wait for parquet conversion, then regenerate the leaderboard

The `leaderboard` command reads from the HF **parquet API**, which lags the push by several minutes to ~30 min. **Poll until the new config appears** before generating, or step 4 will silently use stale data. Run as a background Bash job so it notifies on completion:

```
python3 - <<'PY'
import requests, time, sys
CFG = "2026_06"   # update for the month
url = "https://datasets-server.huggingface.co/parquet?dataset=music-arena/music-arena-dataset"
deadline = time.time() + 3000
while time.time() < deadline:
    try:
        r = requests.get(url, timeout=20)
        if r.status_code == 200 and CFG in {i.get("config") for i in r.json().get("parquet_files", [])}:
            print("READY"); sys.exit(0)
    except Exception as e:
        print(e)
    time.sleep(30)
print("TIMED_OUT"); sys.exit(1)
PY
```

**Then clean old results and regenerate**. On this machine, `results/` files are root-owned (Docker runs as root) — plain `rm -rf` fails "Permission denied" and there is no passwordless sudo. Clean via the same Docker image as root:

```
docker run --rm \
  -v ~/music-arena-leaderboard/components/leaderboard:/lb \
  --entrypoint bash music-arena-comp-leaderboard \
  -c 'find /lb/results -type f -delete'
```

Then:

```
ma-comp leaderboard -s leaderboard
```

Confirm only the new-month TSVs and PNGs appear in `components/leaderboard/results/{leaderboards,plots}` (all filenames should end with the new `YYYYMMDD`). Report the top three for both instrumental and vocal boards.

### Step 5 — Stage the frontend snapshot

**`ma-comp leaderboard -s update-frontend` does NOT work here.** Two bugs:

1. It picks the folder name from `tsv_files[0]` (random glob order) rather than the max end-date, so the folder is often labeled with the wrong month.
2. The Docker container doesn't mount `components/frontend/`, so its `shutil.copy2` writes into the container's ephemeral FS — files never reach the host.

**Copy the four result files manually** to the correctly-named host dir:

```
cd ~/music-arena-leaderboard
DATE=<end-of-month YYYYMMDD, e.g. 20260630>
RES=components/leaderboard/results
DEST=components/frontend/ma_frontend/leaderboard/$DATE
mkdir -p "$DEST"
cp "$RES/leaderboards/"*$DATE*.tsv "$DEST/"
cp "$RES/plots/"*$DATE*.png        "$DEST/"
ls -la "$DEST"   # expect 2 .tsv + 2 .png (instrumental + vocal), matching prior months
```

No frontend code change is needed: `frontend.py` auto-displays the latest dated dir (`sorted(LEADERBOARD_DIR.iterdir())[-1]`).

### Step 6 — Local commit, then stop

**Final action — commit locally and hand off.** Per the maintainer's preference: create a local git commit containing only the new leaderboard snapshot and leave it for them to review and push. **Do not push, do not open a PR** (on this machine, `gh` isn't installed anyway).

Ask before committing. On approval:

```
cd ~/music-arena-leaderboard
git checkout -b 26MM-update      # from main, if not already on it
git add components/frontend/ma_frontend/leaderboard/$DATE/
git status -sb                   # confirm ONLY the new dir is staged
git commit -m "Adds <Month> leaderboard"
```

Then report the commit SHA and hand off.

## Catching up on multiple missed months

If the last release predates the previous calendar month by more than one (e.g. today is August and neither June nor July has been published), `download` will pull the full gap in one shot and `preprocess` splits it into one folder per month automatically (based on each battle's actual timestamp). Confirm the gap up front by comparing `ls ~/music-arena-leaderboard/music-arena-dataset/battle_data/` against today's date, and enumerate the missing months to the maintainer before starting.

**Default: iterate the pipeline once per missing month, oldest-first.** This preserves per-month traceability on HF and per-month snapshots in the frontend history — matching the shape of every prior single-month run. For each missing month M:

1. Run Step 1 with an explicit `--end`:
   ```
   ma-comp leaderboard download --end <last day of month M, YYYY-MM-DD>
   ```
   Omit `--end` on the final month so it defaults to end-of-previous-calendar-month.
2. Run Step 2 (preprocess) — this rewrites all monthly folders each time, cheap.
3. **Surface that month's stats** from `~/.cache/music_arena/bucket/dataset/metadata/<TAG>.md` before pushing: battles, votes A/B/TIE/BOTH_BAD, instrumental vs vocal, unique users, model appearances. Get the maintainer's explicit OK for the push.
4. Continue Steps 3 → 6 for that month (HF commit → parquet wait → leaderboard → frontend snapshot → local commit on a `26MM-update` branch). Each month ends with its own local commit that the maintainer reviews.
5. Repeat for the next missing month.

The maintainer's stated default is: do all missing months in a single session, but be surfaced per-month stats along the way and get consent before each HF push. Do not chain months silently.

**Alternate (only if the maintainer asks): single combined HF push.** Skip the `--end` overrides; download+preprocess produce all missing folders. Copy all new folders into the HF repo, run `update_hf_readme.py` once, commit as `"Add <Month1>–<MonthN> YYYY data"`, push once. Only the latest frontend snapshot is generated (leaderboard is a cumulative snapshot, not per-month). Faster, but you lose per-month HF commit history and per-month frontend dated dirs.

## Gotchas checklist

1. Activate `.venv` in **every** Bash call.
2. Don't run any `monthly_update.sh` (deleted from this repo) — it assumed the dataset repo at `$HOME/music-arena-dataset`. Run steps individually as above.
3. On this machine, Docker writes as root → `cache/` and `results/` are root-owned; clean stale files via a Docker one-liner, not `sudo`.
4. Right after HF push, the parquet API 500s and sanity-check looks broken — **wait/poll** before step 4 rather than treating it as a failure. Trust `git log -1 origin/main`.
5. Set `lfs.concurrenttransfers=2` and `lfs.transfer.maxretries=10` before pushing — the default (8) hits HF's 1000-req/5min rate limit.
6. `update-frontend` is broken on the host in two ways — copy the four result files manually.
7. **Never** stage the nested `music-arena-dataset/` repo or `.claude/` into the main repo; check `git status -sb` before every commit.
8. On this machine, `gh` isn't installed; don't try to open a PR — leave the local commit for the maintainer.
9. If catching up more than one month, use `--end` on `download` to process oldest-first, one month per iteration — see "Catching up on multiple missed months". Never push multiple months to HF in one commit without asking.

## Interaction style

- Present output from each step before advancing; don't chain steps silently.
- Ask before: pushing to HF, cleaning stale `results/`, making the final local commit.
- If a step surfaces a number worth eyeballing (battle counts, top models, LFS object count), state it plainly.
- Do not use `sleep` to wait for HF rate limits or async conversions — use `Monitor` with a proper retry loop, or `Bash run_in_background` with a Python poll script that exits on the terminal condition.
